# ADR-002: слои domain / ports / application / adapters в arm_control

## Контекст

До разделения в `arm_control` было два монолитных `main`: `joint_mover.cpp` и
`cartesian_mover.cpp`. В каждом: создание узла и спиннера, валидация параметров,
нормировка кватерниона, вызовы MoveIt, логи и код возврата. Чтобы поменять точку
назначения демо-движения, нужно было понимать весь файл; чтобы добавить тест на
проверку параметров, нужно было поднимать rclcpp.

## Решение

Четыре слоя, направление зависимостей только вниз:

```text
apps ─► adapters ─► application ─► ports ─► domain
```

- `domain` — типы и инварианты (позы, цели, допуски, статусы, настройки). Только STL.
- `ports` — один интерфейс `MotionPlanner` (контракт исполнителя движения).
- `application` — политика: порядок команд, остановка на первой неудаче.
- `adapters` — MoveIt 2, rclcpp, geometry_msgs.
- `apps` — композиция: собрать слои и передать демо-данные.

Направление обеспечивается **сборкой**, а не соглашением: `arm_control_domain` и
`arm_control_application` не вызывают `ament_target_dependencies` вообще, поэтому
`#include <moveit/...>` в домене не компилируется.

## Последствия

- Тесты домена и приложения линкуются с gtest и STL — не нужен ни ROS-граф,
  ни запущенный move_group (см. `arm_control/test/`).
- Смена планировщика (OMPL → PILZ → свой) затрагивает только `adapters`.
- Чтение и правка одной функции требуют понять: интерфейс порта, один файл
  реализации, тесты слоя. Не «37 файлов».
- Цена — больше файлов и отдельные цели CMake. Для 6-DOF манипулятора с двумя
  командами это оправдано: демо-данные и инфраструктура больше не перемешаны.

## Отклонённые альтернативы

- Один класс `MotionExecutor` с методами `moveJoints`/`movePose` — снова монолит,
  тестируемый только вместе с MoveIt.
- Ввести ECS или общий event bus — избыточно для двух команд, ломает локальность.
